# 7.9 Inline functions and variables

> 原文：https://www.learncpp.com/cpp-tutorial/inline-functions-and-variables/

## 核心概念

- **两种实现选择**：写一段小任务代码时，可以直接内联写进已有函数里，也可以新建一个函数。
- **小函数的好处**：更易读、模块化、可复用，修改只需改一处。
- **函数调用开销（overhead）**：每次调用都要保存当前指令地址与 CPU 寄存器、实例化并初始化参数、跳转到函数、跳回、拷贝返回值。Overhead 指为设置、支撑或收尾一个任务所需的额外工作。
- **开销何时重要**：对大型/复杂函数可以忽略；对**短小而频繁调用**的函数，调用开销可能超过执行函数本身的时间。
- **内联展开（inline expansion）**：一种把函数调用替换为被调函数体（实参代入形参）的过程。除省去调用成本外，展开还常让编译器做进一步优化（如把表达式在编译期算成常量）。
- **展开的代价**：若展开后的函数体指令数多于被替换的调用，可执行文件会变大，而更大的程序因缓存效应往往更慢。
- **不确定的权衡**：是否展开取决于调用成本、函数大小与其它优化，结果可能更好、更差或不变。
- **最佳候选**：简短函数（大约几条语句），尤其是被频繁重复执行（如循环内）的调用点。
- **两类函数**：调用"可能被展开"（大多数函数）或"无法展开"。编译器对每个函数、每个调用点分别评估，可能不展开、部分展开或全部展开。
- **常见的"无法展开"情形**：函数定义位于**另一个翻译单元**，编译器看不到可替换的内容。
- **`inline` 的历史用途**：最初是"此函数可能值得展开"的提示；用 `inline` 声明的函数叫**内联函数（inline function）**。
- **为何语义变了**：请求展开属于过早优化，提示可能被忽略，且关键字作用于定义而展开是按调用点决定的。
- **现代含义**：`inline` 现在表示**允许多个定义**——内联函数可在多个翻译单元中定义而不违反 ODR。
- **内联函数的要求**：使用它的每个翻译单元都必须能看到其完整定义（仅有前向声明不够）；每个翻译单元只允许一个定义；对外部链接的内联函数，所有定义必须完全相同，否则行为未定义。（定义可以在使用点之后出现——只要此前有前向声明；但这样一来该使用点之前可能不会展开。）
- **链接器行为**：链接器把所有内联定义合并为一个定义，从而满足单一定义规则。
- **历史联系**：因为展开要求每个翻译单元都能看到定义，平凡函数常被拷贝多份；把内联函数豁免于单一定义规则正好解决此问题，关注点也由"展开"转移到"ODR 豁免"。
- **为何 ODR 豁免合理**：重复的非内联定义暗示命名冲突与调用歧义；而多个内联定义被默认为"同一个函数"，因此任一都能匹配调用。
- **典型放置**：内联函数通常定义在**头文件**中，让每个包含者都看到相同的完整定义；这支撑了**仅头文件库（header-only library）**——无需源文件、无需链接。
- **隐式内联的函数**：在类/结构体/联合体内定义的函数；`constexpr`/`consteval` 函数；由函数模板隐式实例化得到的函数。
- **内联变量（C++17）**：允许在多个文件中定义的变量，要求与内联函数相同（处处可见相同的完整定义）。
- **隐式内联的变量**：静态 `constexpr` 数据成员；与 `constexpr` 函数不同，`constexpr` 变量默认**不是**内联的。

## 最佳实践

- **Tip**：现代优化编译器自行决定何时把函数内联展开。
- **Best practice**：不要用 `inline` 关键字来"请求内联展开"你的函数。
- **Rule**：编译器必须在内联函数被使用的每一处都看到其完整定义，且外部链接的内联函数的所有定义必须完全相同，否则行为未定义。
- **Best practice**：除非有特别充分的理由（例如在头文件中定义函数或变量），否则避免使用 `inline`。

# 7.14 Unnamed and inline namespaces

> 原文：https://www.learncpp.com/cpp-tutorial/unnamed-and-inline-namespaces/

## 核心概念

- **两种命名空间变体**：C++ 提供匿名（unnamed）命名空间与内联（inline）命名空间。作者称"We won't build on these, so consider this lesson optional for now"（后续不会依赖它们，暂可视为选学）。
- **匿名（unnamed）命名空间**：不带名字的命名空间，写作 `namespace { ... }`。
- **成员并入父命名空间**：其中声明的一切被视为属于外层命名空间，因此可不必加前缀直接调用。
- **内部链接**：匿名命名空间内所有标识符实际上具有内部链接，即在定义它的文件之外不可见。
- **大致等价于 `static`**：对函数而言，这等同于在文件作用域把它们声明为 `static`。
- **主要用例**：把大量"文件局部"内容归拢在一处，比逐个声明 `static` 更整洁；它还能让程序自定义类型成为翻译单元局部（此点 `static` 没有对应替代）。
- **Tip（作者附注）**：更严格的做法是把所有"并不打算导出/外部使用"的内容都放进匿名命名空间。
- **头文件限制**：匿名命名空间一般不应出现在头文件中；作者引用 SEI CERT 规则 DCL59-CPP 说明原因。
- **内联命名空间**：用 `inline` 关键字标记的命名空间，常用于对内容做版本管理。与匿名命名空间一样，其内容属于父命名空间；但与匿名命名空间不同，它**不改变链接性**。
- **版本管理行为**：使用非限定名的调用者自动得到内联版本，而显式限定仍可访问其它版本，从而保持既有代码不变。
- **反转默认**：把较新的命名空间设为 inline，会把新行为强加给既有调用者，它们可能被迫去改全局限定。
- **两者结合**：命名空间可同时既 inline 又匿名，但作者建议改为"在 inline 命名空间内嵌套匿名命名空间"，效果相同（内部链接）又能保留一个显式命名空间名。

## 最佳实践

- **Best practice**：当有想保持为单个翻译单元局部的内容时，优先使用匿名命名空间。
- **Best practice**：避免在头文件中使用匿名命名空间。
- **Tip**：更严格的风格是把所有"并非明确打算导出、供外部使用"的内容都放进匿名命名空间。

# 8.14 Generating random numbers using Mersenne Twister

> 原文：https://www.learncpp.com/cpp-tutorial/generating-random-numbers-using-mersenne-twister/

## 核心概念

1. **先包含头文件**：C++ 的随机数功能都在标准库的 `<random>` 头文件中。
2. **Mersenne Twister 是最广泛使用的 PRNG**：它有点老，但一般能给出质量不错的结果，性能也尚可。
3. **两种 Mersenne Twister 类型**：`mt19937` 产生 32 位无符号整数；`mt19937_64` 产生 64 位无符号整数。
4. **基本用法**：用 `std::mt19937 mt{};` 实例化引擎，每次需要下一个 32 位无符号随机值时调用 `mt()`。
5. **关于 `mt()`**：它是成员函数 `mt.operator()` 的简写，返回序列中的下一个值。用运算符形式不必记住函数名，也更短。
6. **PRNG 只生成其完整范围**：32 位引擎输出 0 到 4,294,967,295，因此要模拟骰子或伤害范围，需要转换它的输出。
7. **朴素的范围转换很难无偏**：自己写一个正确、无偏的转换器并不简单。
8. **随机数分布（distribution）**：分布把 PRNG 的输出转换成另一种分布（以 PRNG 值为输入的概率分布）。
9. **均匀分布**：最通用的一种：以相等概率产生 X 到 Y（含端点）之间的输出。
10. **默认播种的缺陷**：值初始化引擎（`std::mt19937 mt{};`）每次运行都以相同种子播种，因此整个序列在多次运行间重复——单个值相对前一个值看似随机，但序列本身不变。
11. **为什么重要**：像猜数字这样的游戏，如果电脑每次都选同一个数就索然无味。
12. **修复：每次运行都变化的种子**：不需要随机种子——只需每次执行都不同即可，这样 PRNG 就能推导出唯一序列。
13. **方法 1——系统时钟**：用 chrono 库的时钟取"从最早可测量时刻起经过的 tick 数"。这里偏好 `std::chrono::steady_clock`，因为用户无法调整它。
14. **时钟播种的局限**：快速连续运行的程序可能得到几乎相同的种子，削弱需要高度独立结果的程序的统计质量。
15. **时钟选择的提示**：`std::chrono::high_resolution_clock` 粒度最细，但可能关联到系统时钟，用户可更改或回拨；`steady_clock` 的 tick 较粗，但保证不可调整。
16. **方法 2——random device**：`std::random_device` 是实现定义的 PRNG，通常向操作系统索取伪随机数。它是"避免使用实现定义类型"这一建议被接受的例外之一。
17. **`std::random_device` 的注意点**：它不要求是非确定性的，在某些系统上可能每次运行产生相同序列。一个 MinGW 的 bug（GCC 9.2 修复）正是如此。当前 GCC/MinGW、Clang、Visual Studio 都提供了正确的实现。
18. **为什么不直接把 `std::random_device` 当生成器用？** 因为它实现定义、可能开销大或阻塞、其随机数池会很快耗尽（影响其他使用同一来源的应用）。它更适合用来播种。
19. **只播种一次**：重新播种会重新初始化生成器状态，通常会让结果更不随机，甚至完全不随机。
20. **常见的新手错误**：在会被反复调用的函数内部创建并播种新引擎——低效且很可能产生很差的随机性。
21. **Mersenne Twister 的状态大小**：内部状态需要 19937 位（2493 字节）= 624 个 32 位值或 312 个 64 位值，因此 `std::mt19937` 分配 624 个整数，`std::mt19937_64` 分配 312 个。
22. **关于分配整数类型的旁注**：`std::mt19937` 使用 `std::uint_fast32_t`，其在某些架构上可能是 64 位——可能使其内存需求翻倍。
23. **播种不足（underseeding）**：用单个整数播种意味着 624 个整数都由一个值初始化；库尽力填充其余 623 个但无法变魔术。举例：用单个 32 位值播种 `std::mt19937`，其首个输出永远不会是 `42`。
24. **`std::seed_seq` 作为部分修复**：这个类型接受你提供的任意多个随机值，并生成额外的无偏种子值来填满 PRNG 的状态。只给一个值时它会再产生 623 个值——改善了 0/1 位的混合，但不增加随机性。
25. **更好的 `std::seed_seq` 用法**：提供 8 个来自 `std::random_device` 的值能得到好得多的种子数据；这被描述为最简单省力的改进。
26. **为什么不提供 624 个值？** 可能很慢，且有耗尽 `std::random_device` 池的风险。其他"随机"输入（时钟、线程 id、函数地址、用户 id、进程 id）也可以混入，但超出本文范围。
27. **替代路径**：选择一个状态较小的 PRNG——许多优秀的只用 64 或 128 位，很容易用 `std::seed_seq` 加 8 次 `std::random_device` 调用来播种。
28. **预热（warming up）PRNG**：丢弃前 N 个输出可让内部状态充分混合，之后的结果质量更高。通常丢弃几百到几千个；长周期 PRNG 需要更多。
29. **关于 `rand()` 的旁注**：Visual Studio 的实现有个 bug，首个结果不够随机；较老的程序会丢弃一个结果来绕过。
30. **`mt19937` 无需手动预热**：它的 `seed_seq` 初始化本身已执行了预热。
31. **跨多个函数/文件使用随机数**：该内容已移到 8.15 节——Global random numbers (Random.h)。
32. **用固定种子调试**：随机程序每次行为不同，临时用特定固定值（如 5）播种可复现 bug 行为；递增种子直到错误出现，再恢复正常播种。
33. **FAQ——每次运行序列相同**：生成器可能没有正确播种，或根本没播种；用每次运行都变化的值播种它。
34. **FAQ——反复出现同一个数**：你可能在每次抽取前都重新播种，或为每个随机数都构造一个新生成器。

## 最佳实践

- **Tip**：`std::chrono::high_resolution_clock` 是 `steady_clock` 的热门替代品，粒度最细，但它可能依赖系统时钟，用户可更改或回拨；只有 `steady_clock` 保证不可被用户调整。
- **Best practice**：Use `std::random_device` to seed your PRNGs（除非你的目标编译器/架构没有正确实现它）。
- **Best practice**：Only seed a given pseudo-random number generator once, and do not reseed it.

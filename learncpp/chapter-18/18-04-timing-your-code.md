# 18.4 Timing your code

> 原文：https://www.learncpp.com/cpp-tutorial/timing-your-code/

## 核心概念

- **为何给代码计时**：当你拿不准两种写法哪个更快时，测量各自耗时是简单的判断办法。
- **chrono 直接用很别扭**：C++11 在 `chrono` 库中提供计时工具，但作者称它们“有点晦涩（a bit arcane）”，因此建议把它们封装成一个小类。
- **Timer 类（设计）**：把 `Clock` 别名到 `steady_clock`（单调时钟，适合计时），把 `Second` 别名到 `std::chrono::duration<double, std::ratio<1>>`（以秒为单位），并在构造时存下一个起点 `time_point`。
- **`reset()`**：通过把 `Clock::now()` 赋给存下的时间点来记录新的起点。
- **`elapsed()`**：用 `duration_cast` 和 `count()` 返回从起点到现在经过的秒数（`double`）。
- **用法模式**：在希望开始计时处构造一个 `Timer`，需要时间时随时调用 `elapsed()` 得到已过去的秒数。
- **选择排序基准**：用本章的选择排序对 10,000 个元素排序，约 0.05 秒（作者三次测量 0.0507 / 0.0506 / 0.0498）。
- **`std::sort` 基准**：同样测试改用标准库排序，约 0.0007 秒（0.000693 / 0.000692 / 0.000699）。
- **主要结论**：此例中库排序比手写选择排序快约 100 倍。
- **要用 release 构建**：debug 目标通常关闭优化，会严重歪曲结果；作者的 debug 版 `std::sort` 例子耗时 0.0235 秒，约长 33 倍。
- **后台系统活动有影响**：CPU、内存或磁盘密集的任务（游戏、杀毒扫描、系统更新，甚至空转的浏览器轮播广告）会扰动计时；关闭这些应用可减少波动。
- **随机数生成会歪曲计时**：不同的随机序列会改变工作量（例如交换次数），所以用字面量作种子能得到可重复的运行；但若性能强烈依赖序列，也可能产生误导。
- **不要把等待用户输入计入**：等人花的时间不该算进性能；可通过命令行、文件或旁路代码路径提供输入。
- **至少测三次**：结果相近说明测到的是真实性能；否则继续测量，直到结果聚集并能识别出离群值。
- **方差大意味着受到干扰**：分散度很大说明系统或程序的随机化正在影响结果。
- **绝对 vs 相对测量**：绝对时间跨不同机器意义不大；在同一台机器上比较两个变体才有用。
- **用重测变体 1 作健全性检查**：若变体 1 的第二次测量与第一次一致，说明两个变体得到了公平比较；若不一致，则机器状态已改变，应丢弃结果并重做。

## 最佳实践

- 本节原文没有标注的 **Best practice** / **Author's note** / **Warning**。其中接近“警告”的是性能部分的行文告诫：
  - 使用 **release 构建**而非 debug 构建来测量。
  - 不要在系统繁忙时测量（关闭后台应用以减小方差）。
  - 不要把“等待用户输入”的时间计入性能测量。

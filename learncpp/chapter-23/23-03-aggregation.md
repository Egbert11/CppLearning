# 23.3 Aggregation

> 原文：https://www.learncpp.com/cpp-tutorial/aggregation/

## 核心概念

- **组合的回顾**：上一节讲了对象组合——用更简单的对象搭出复杂对象，其中整体对部分的存在负责。
- **聚合的定义**：当整体/部分关系满足以下四条时，就是**聚合（aggregation）**：部分是类的一部分；部分"（如需要）可以同时属于多个对象（类）"；其存在**不由**该类管理；部分"不知道对象（类）的存在"。
- **仍是部分-整体、仍是单向**：部分位于整体之内，关系指着一个方向——但与组合不同的是，部分可以被共享、可以比整体活得更久。
- **不承担生命周期责任**：聚合被创建时不会创建其部分；被销毁时也不会销毁它们。
- **例子——人与地址**：一个地址可被室友或伴侣共享，多半在"人"之前就存在、并在"人"之后仍存在；人知道地址，地址不知道它的住户。
- **例子——车与引擎**：引擎是车的一部分，但也可以属于车主；车不创建也不销毁引擎；车知道它的引擎，引擎不知道车。
- **关于"被销毁"的 caveat**：陨石砸毁一辆车可能连零件一起毁了，但那是外部力量——关键在于车**不负责**销毁零件。
- **"has-a" 建模**：聚合建模 has-a 关系（一个系有教师，一辆车有引擎）。
- **部分可单个也可多个**：与组合一样，聚合可以持有一个部分或多个部分。
- **实现几乎与组合相同**：区别主要是语义上的；聚合通常把部分存为**引用或指针**，指向在类之外创建的对象。
- **部分如何进入**：或者作为构造函数参数传入，或者聚合先为空、之后再通过访问函数或运算符添加部分。
- **析构行为**：类被销毁时，指针/引用成员被销毁但**不会**被 delete——部分依然存活。
- **Teacher/Department 走查**：`bob` 独立创建，被传给 `department` 的构造函数；department 死亡时只有引用死亡，所以 `bob` 依然存在。
- **建模指导**：不要按"看起来现实"来选，而要选**满足程序需求的最简单关系**。修车厂模拟器可能会聚合 car/engine；赛车模拟器则可能组合它们，因为引擎从不脱离车存在。
- **小结——组合（compositions）**：通常用普通成员变量；若类自己管理分配/释放，则可用指针；负责创建与销毁部分。
- **小结——聚合（aggregations）**：通常用指针/引用成员，指向类作用域之外的对象；**不**负责创建与销毁部分。
- **允许混用**：一个类可以组合一部分、聚合另一部分——例如 Department 拥有自己的名字，却只引用 Teachers。
- **聚合的危险**：它不会释放部分；清理落到外部一方，忘记清理（或丢失指针）就会泄漏内存——所以组合更可取。
- **定义并不精确**：聚合的定义没有统一标准；其他参考资料的定义可能不同。
- **别混淆术语**："aggregate data types（聚合数据类型）"（把变量组合在一起的结构体/类）与"aggregate class（聚合类）"（没有用户提供的构造函数/析构函数/赋值、成员全 public、无继承的 POD 结构体）都与 aggregation 无关。
- **`std::reference_wrapper` 的用途**：像 `std::vector` 这样的容器不能持有引用，而指针又允许为空；`std::reference_wrapper` 行为像引用，却支持赋值与拷贝。
- **要记住的三点**：它定义在 `<functional>`；被包裹的对象不能是匿名临时对象（有悬垂风险）；用 `get()` 成员取出被包裹对象。

## 最佳实践

- **Best practice**：实现"满足程序需求的**最简单**关系类型"，而不是"看起来现实"的那种。
- **Warning**：聚合的定义并不精确，其他参考资料可能定义不同。同时，aggregation 与 **aggregate** 类型（"aggregate data types"、"aggregate class"）是不同概念，不要混为一谈。
- **Author's note（隐含警告）**：聚合把释放交给外部一方，若该方丢失引用或忘记清理就会泄漏——因此能组合时优先组合。

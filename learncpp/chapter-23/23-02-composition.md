# 23.2 Composition

> 原文：https://www.learncpp.com/cpp-tutorial/composition/

## 核心概念

- **对象组合（object composition）**：用更简单的对象拼装出复杂对象，正如汽车由车架、引擎、轮胎、变速箱组装，计算机由 CPU 与主板组装。
- **"has-a" 关系**：组合广义上建模"一个对象包含另一个对象"——汽车"有一个"变速箱，计算机"有一个"CPU。
- **整体与部分术语**：复杂对象叫**整体（whole）/父（parent）**，简单对象叫**部分（part）/子（child）/组件（component）**。
- **复合类型**：既然结构体/类可以持有基础类型或类类型的数据成员，构造这样的类本身就是在做组合；这类类型有时被称为"**复合类型（composite types）**"。
- **为何有用**：把复杂类拆成简单、可管理的零件，能降低复杂度、减少错误、加快开发，因为可复用已有的、经过测试的代码。
- **两个子类型**：对象组合分为**组合（composition）**与**聚合（aggregation）**（聚合见下一节）。
- **术语caveat**："composition" 常被宽松地泛指两种子类型；本教程用"object composition"指广义概念，用"composition"指具体的子类型。
- **组合的四条要求**：(a) 部分是对象的一部分；(b) 同一时刻只能属于一个对象；(c) 由对象管理其存在；(d) 不知道对象的存在。
- **部分-整体关系**：部分构成整体的一部分，且不能同时属于两个整体——例如一颗心脏只属于一个身体。
- **对象拥有部分的生命周期**：通常部分随对象创建、随对象销毁；更一般地，对象负责管理生命周期，使用者无需操心。因此组合被戏称为"death relationship（生死相随的关系）"。
- **单向可知（unidirectional）**：整体知道部分，部分对整体一无所知；作者称之为"**单向**"关系。
- **可转移性无关**：组合不规定部分能否被移动；移植过来的心脏只要此后只属于受体，就仍满足组合规则。
- **"part-of" 建模**：组合更准确地说是 "part-of" 关系（分子是分数的一部分），常用于物理上的包含关系。
- **部分可单个也可多个**：身体有一颗心脏，但有十根手指；多个部分可用数组建模。
- **实现方式**：组合是最容易编码的关系之一——普通结构体/类，用普通数据成员，其生命周期绑定到外层实例。
- **动态分配情形**：若需要分配/释放，可用指针成员，但**组合类自身**必须处理所有内存管理，而不是它的使用者。
- **优先规则**：如果一个类**能**用组合设计，就**应该**用组合；这样的类被描述为简单、灵活、健壮。
- **Point2D/Creature 示例**：2D 世界中的生物持有名字和位置；位置用一个单独的 Point2D 类建模，于是 Creature 是其各部分的组合。
- **Point2D 设计**：用两个整数维度（X、Y）表示离散方格世界；默认构造函数初始化为 0；带两参构造函数；friend `operator<<` 打印 `(x, y)`；`setPoint` 修改器。所有函数都写在头文件里，所以没有 `Point2D.cpp`。
- **Creature 设计**：持有 `std::string` 名字与 `Point2D` 位置；构造函数接收 `std::string_view` 与 `const Point2D&`；提供 friend `operator<<` 和把工作转交给 `setPoint` 的 `moveTo`。
- **驱动程序**：`main` 询问生物名字，在 `{4, 7}` 处构造它，然后循环打印生物、读取新的 X 和 Y 坐标，任一为 `-1` 时退出。
- **组合的变体**：部分可以延迟到首次需要时才创建（如 string 的动态字符数组）；可以作为输入被提供而非自行创建；其销毁可以委托给别处（如垃圾回收器）。
- **变体之上的原则**：无论细节如何变化，组合都必须自己管理其部分，使组合的使用者永远不需要操心。
- **成员类 vs 直接实现**：初学者常问何时该引入一个成员类而非内联实现；使用专门的类有三个好处：(a) 类更聚焦、更简单、更易理解；(b) 类自包含、可复用；(c) 外层类把繁重工作委托出去，只协调数据流，复杂度降低。

## 最佳实践

- **Tip（单一职责）**：每个类应只为完成**单一任务**而构建——要么负责存储/操作数据（如 Point2D、std::string），要么负责协调其成员（如 Creature），最好不要两者兼有。Creature 不需要知道点或名字是如何实现的，它只协调成员"做什么"，由成员决定"怎么做"。
- **Tip（优先组合）**：如果一个类**能**用组合来设计，就**应该**用组合。（原文以 Tip 形式给出的偏好：能用组合就用组合。）

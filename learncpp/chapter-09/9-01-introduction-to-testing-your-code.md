# 9.1 Introduction to testing your code

> 原文：https://www.learncpp.com/cpp-tutorial/introduction-to-testing-your-code/

## 核心概念

- **只运行一次的程序**：如果某个程序只为你当初编写它的那个场景服务、之后再也不会运行，那么验证那一个场景就够了。
- **无输入、无条件的直线式程序**：这类程序跑一遍、检查输出，实际上就等于完整测试过；不过仍可能想在多台机器上运行以捕捉未定义行为导致的不一致。
- **典型的真实程序**：会反复运行、使用循环与条件、读取用户输入、使用可复用函数、发生计划外的范围蔓延（scope creep），或者要发布给他人使用，因此需要跨大量条件主动验证。**程序对某一组输入工作正常，并不保证对所有输入都正确**。
- **软件测试 / 软件验证（software testing / validation）**：确定软件是否真的按预期工作的过程。
- **测试的挑战**：用户输入或条件分支的每一处都把可能的执行路径成倍放大，因此穷举测试几乎立刻变得不可行。示例中的"比较两个 4 字节整数"程序在 4 字节整数假设下大约需要 1800 京（18 quintillion）次运行。
- **用等价类减少测试数量**：如果某一对满足 x > y 的值工作正常，那么所有满足该关系的值对逻辑上也应正常，因此每个分支各跑一次、共约三次运行即可获得较高置信度。
- **分小块测试（汽车比喻）**：在整合前后分别测试、重测每个部件（方案 a），要优于把所有部件装好后只在最后测试（方案 b），因为这样能在部件还小、还孤立时发现问题。
- **涟漪效应（ripple effect）**：一个缺陷可能引发连锁的重新设计；把组件隔离能限制问题传播的范围。
- **单元测试（unit testing）**：在隔离状态下测试一小段代码，以确认该"单元"是正确的；每个单元测试验证该单元的一个特定行为。
- **单元测试框架（unit test framework）**：用于简化编写、维护和运行单元测试的第三方工具（本节不展开）。
- **集成测试（integration testing）**：把单元组合成程序后再重测，以确认它们被正确地连接在一起；它更复杂，目前对程序跑几遍抽查即可。
- **非正式测试**：写完一个单元后随手写一段用完即弃的测试代码，通过后就删掉。
- **保留测试**：与其删除测试，不如把它们搬进一个可复用的测试函数，以便日后（例如修改函数后）重新运行。
- **自动化测试**：测试函数可以同时持有检查与期望答案并自行比较，返回一个失败指示，而不再需要人工核对。
- **使用 `assert`（进阶）**：`assert` 在失败时中止程序并报错，可省去记录测试用例编号的麻烦；详见 9.6。
- **何时开始测试**：一旦写出了非平凡的（non-trivial）函数，就应立刻开始测试。

## 最佳实践

> **Best practice**：Write your program in small, well defined units (functions or classes), compile often, and test your code as you go.
> （把程序写成一个个体量小、定义良好的单元（函数或类），经常编译，并边写边测。）

**For advanced readers**：比"返回失败测试编号"更好的做法是用 `assert`——测试失败时它会带着错误信息中止程序。

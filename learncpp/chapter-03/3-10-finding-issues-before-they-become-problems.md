# 3.10 Finding issues before they become problems

> 原文：https://www.learncpp.com/cpp-tutorial/finding-issues-before-they-become-problems/

## 核心概念

### 尽早发现问题

- **语义错误会潜伏**：语义错误在运行程序的那一刻可能并不明显，可以一直潜伏着，直到后续代码或环境变化才暴露成故障。
- **拖延使错误更难**：bug 在代码库中未被发现的时间越长，通常越难定位；原本"随手一改"的小问题会变成漫长的调试。

### 预防清单（减少错误）

- 遵循最佳实践；
- 避免在疲惫或沮丧时编程；
- 了解语言的常见陷阱；
- 让函数保持短小；
- 尽量使用标准库，而不是自己造轮子；
- 多写注释；
- 从简单的设计开始，逐步增加复杂度；
- 避免"聪明"的解法；
- 把可读性与可维护性置于速度之上。

### 重构（Refactoring）

- 定义：在不改变行为的前提下对代码做**结构性修改**。目的是通过改善组织与模块化来降低复杂度。
- **函数长度指导**：一个占满整屏的函数通常被认为太长——若需要滚动才能读完，理解度会明显下降。理想情况下函数应少于 10 行，少于 5 行更好。
- 长度不是真正的目标：真正目标是**可理解性与可维护性**。为了省一两行而放弃良好实践、或用晦涩技巧，是本末倒置。

### 防御性编程（Defensive programming）

- 定义：预想软件被误用的**所有**方式——被终端用户误用，或被其他开发者（包括你自己）误用——然后检测并缓解这些误用。例如，对输入了错误数据的用户提示其重试。错误处理在后续课程讲解。

### 尽早发现错误

- 大程序中不可能避免所有错误，所以次优的做法是**尽快发现它们**：写少量代码就立刻测试，确认它能正常工作。

#### 测试函数与单元测试

- 一种常见做法是编写**测试函数**来"exercise"（检验）你的代码。
- **单元测试（unit testing）**：一种测试小型代码单元正确性的方法。存在第三方的单元测试框架；自己写也可以，但需要更多目前尚未讲到的语言特性。

#### 基于约束的技术

- 这类技术会加入额外代码（可在非 debug 构建中被编译掉）来验证"假设/期望"未被违反。
- 阶乘的例子：一个期望参数非负的函数，可以检查调用者传入的值，若为负就立即报错，而不是返回一个不确定的结果。
- 参见 `assert` 与 `static_assert`（第 9.6 课）。

#### 静态分析工具（linters）

- 定义：不执行代码就检查源码的程序（"静态"指不执行），用来标记特定的语义问题。
- 它的发现未必是当前问题的成因，但能揭示代码中脆弱的地方。
- **你的编译器也是静态分析工具**：除了检查语法，多数现代 C++ 编译器会做轻度静态分析——例如警告未初始化的变量。提高编译器的警告/错误级别（第 0.11 课）有助于暴露这些问题。
- 适用范围：静态分析工具很多（原文链接了 Wikipedia 的工具列表），有的能检测 300 多种错误。对小型教学程序它是可选的；但对发现"不符合最佳实践"之处很有价值；大型程序上**强烈推荐**，因为工具可能暴露数十甚至数百个问题。

## 最佳实践

- **Best practice**：在你的程序上使用静态分析工具，帮助找到代码中不符合最佳实践的地方。
- **Key insight（关键洞见）**：要么改行为、要么改结构，改完再测试（make behavioral changes **OR** structural changes, and then retest）。同时做行为改动和结构改动，往往会产生更多、更难定位的错误。

### 其它提示与工具

- **Visual Studio**：2019 及更高版本内置静态分析工具，通过 *Build > Run Code Analysis on Solution (Alt+F11)* 使用。
- **常用静态分析工具（免费）**：clang-tidy、cpplint、cppcheck（已集成进 Code::Blocks）、SonarLint。多数有 IDE 扩展，例如 Clang Power Tools 扩展。
- **付费工具（对开源项目可能免费）**：Coverity、SonarQube。
- **原文引语**：Brian Kernighan《The Elements of Programming Style》第 2 版——"Everyone knows that debugging is twice as hard as writing a program in the first place."（调试的难度是写程序的两倍。）若把代码写得尽可能"聪明"，那要如何调试它？——这正是应避免不必要"聪明"解法的论点。

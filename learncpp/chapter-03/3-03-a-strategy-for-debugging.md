# 3.3 A strategy for debugging

> 原文：https://www.learncpp.com/cpp-tutorial/a-strategy-for-debugging/

## 核心概念

- **时间花在哪**：调试的大部分精力都用在"定位错误"上；一旦找到错误，修复它并验证修复通常要简单得多。
- **靠读代码找问题**：在较小的程序里，错误的性质和程序结构往往能提示出可能的位置，有时仅凭阅读就能发现。
  - 举例：如果名字被按逆字母序打印出来，那么罪魁祸首很可能就是那个排序函数。
- **为什么靠读代码会变难**：要读的代码更多（上千行时非常枯燥）；代码更复杂、出错点更多；程序行为可能几乎给不出线索（例如程序什么都不输出）。
- **错误的假设**：由错误假设引发的 bug 几乎无法靠阅读发现，因为你在检查代码时会不自觉地重复同一个假设。
- **靠运行程序找问题**：当阅读法失灵时，转而去观察运行时的行为。总体思路是：
  1. 弄清如何复现问题；
  2. 运行并收集信息，缩小问题所在范围；
  3. 重复上述过程，直到找到问题。
- **复现问题是第一步、也是最关键的一步**：要让问题稳定地出现，因为"除非你能观察到问题发生，否则极难找到它"。
  - 制冰机类比：如果每次你去试制冰机它都正常出冰，那就几乎无从诊断；能看到故障才谈得上诊断。
- **容易 vs 困难的复现**：显而易见的问题（例如稳定崩溃）容易复现；有些问题只在特定机器或特定输入下才出现，此时把复现步骤写下来会很有帮助。
- **复现步骤（reproduction steps）定义**："一份清晰、精确的步骤清单，照着做能以很高的可预测性让问题重现。" 理想情况是 100% 复现；若是 50%，因为你有一半运行得不到诊断信息，诊断时间大约翻倍。
- **逐步逼近问题**：借鉴"猜数字"游戏——每次猜测得到"太高""太低"或"正确"，从而快速收敛（在 1~10 的情况下，最优不超过 4 次即可猜中）。
- **把猜数字套用到代码上**：bug 一定位于"程序开始"到"第一个可观察到的不正确症状"之间；这能排除之后的代码，但区间内仍可能有很多代码。
- **初始猜测**：症状通常会暗示一个相近的起点（例如"写文件失败"会把注意力引向写文件的那段代码）。
- **"太低"的情形**：若能在某个执行点证明问题尚未发生，那么问题必然在其之后——就像回答"太低"。例：程序在某点 X 之前还没崩溃，那么崩溃必然发生在 X 之后。
- **"太高"的情形**：若在某个点已观察到错误行为，那么 bug 就在更早处——就像回答"太高"。例：变量 *x* 本应为 2 却打印成 8；若某个时刻 *x* 已经是 8，那么 bug 出现在那之前。
- **类比的局限**：有时能整段整段地排除代码，却无法判断 bug 在那段之前还是之后。
- **收敛**：配合足够多的猜测和好技巧，最终能定位到具体的那一行，这同时也会暴露出错误的假设。
- **策略的选择**：最好的猜测方式取决于 bug 的类型；要多尝试不同方法，经验会让直觉越来越准。

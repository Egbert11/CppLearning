# 10.9 Type deduction for functions

> 原文：https://www.learncpp.com/cpp-tutorial/type-deduction-for-functions/

## 核心概念

- **编译器会检查显式返回类型**：当函数声明了返回类型，编译器会判定返回表达式的类型，并核实它是否匹配（或可转换为）声明的类型。
- **`auto` 返回类型推导（C++14）**：既然编译器本就会检查 `return` 语句，`auto` 关键字被扩展用于替代函数的返回类型，让编译器从返回值推导它。
- **一致性规则**：使用 `auto` 返回类型时，函数中所有 `return` 语句必须产生相同类型，否则编译失败。
- **混合返回的两种补救**：要么写明显式返回类型，让编译器隐式转换不匹配的表达式；要么显式地把所有返回值转成同一类型——例如把 `5` 写成 `5.0`，或对非字面量用 `static_cast`。
- **好处：避免返回类型不匹配**：推导消除了返回类型与返回值对不上的风险，防止了不想要的隐式转换。
- **好处：返回类型易变**：当函数返回类型很可能随实现而变时，推导省去了手工更新所有相关返回类型的麻烦。
- **好处：复杂或不清晰的类型**：对于冗长、复杂或不直观的返回类型，`auto` 简化了代码（如何显式命名这类类型见 11.8）。
- **坏处 1 —— 必须先定义再使用**：返回 `auto` 的函数必须在任何调用前完整定义，因为前向声明提供的信息不足以推导类型；在作者机器上示例报错：
  `error C3779: 'foo': a function that returns 'auto' cannot be used before it is defined.`
  这类函数通常只能在其所在文件内调用。
- **坏处 2 —— 接口不透明**：与对象推导不同（初始化式就在同一语句里），函数原型完全不透露推导出的返回类型，读者必须打开函数体（好的 IDE 有帮助）。本节说错误更易发生，接口应当显式。
- **总体建议**：本节指出这里比对象推导更缺乏共识，通常建议**避开**函数的返回类型推导。
- **尾置返回类型（trailing return type）语法**：`auto` 出现在参数前，真正的返回类型放在 `->` 之后；此处 `auto` 不做推导，只是语法。
- **为什么用尾置返回**：
  1. 复杂返回类型更易读；
  2. 连续的声明能对齐；
  3. 依赖参数类型的返回类型无法写在常规位置，因为编译器还没看到参数；
  4. 某些高级特性（如 lambda）要求这种语法。
- **语法建议**：除非需要尾置形式，否则保持传统的返回语法。
- **形参类型不做推导**：C++20 之前，在函数形参上写 `auto` 是编译错误。C++20 下这样的代码能编译，但那里的 `auto` 触发的是函数模板，而非类型推导。

## 最佳实践

- **Best practice**：优先使用显式返回类型，而非返回类型推导——除非返回类型不重要、难以表达或易变。
- **For advanced readers**：必须从参数类型推导返回类型的函数无法使用常规返回类型；某些高级特性（如 lambda）强制要求尾置返回语法。
- **Related content**：函数模板见 11.6；该语境下 `auto` 见 11.8。
